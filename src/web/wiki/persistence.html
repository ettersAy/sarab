Filesystem Persistence

SARAB stores all data on disk under /srv/dev/sarab/projects/. Each project is a directory, with tickets and prompts as editable markdown files. A JSONL cache layer provides fast startup and in-memory querying. No database required.

Directory Layout

/srv/dev/sarab/projects/
  my-project/                   # Slugified project name
    project.json                # Project metadata (id, name, rootPath, settings)
    tickets/
      backlog/                  # One .md file per ticket
        implement-auth-abc123.md
        fix-nav-xyz789.md
    prompts/                    # One .md file per job prompt
        setup-db-def456.md
        deploy-ghi012.md
  another-project/
    project.json
    tickets/backlog/
    prompts/

Project Creation: Local Path vs GitHub Clone

Projects support two creation modes:

ModerootPathBehavior
LocalRequiredMust point to an existing directory. Validation fails if path doesn't exist.
GitHubOptionalClones repo via git clone --depth 1 to auto-generated path (/srv/dev/sarab/repos/[name]). Can override with custom rootPath.

When repoUrl is set, the git service (src/services/git.ts) validates the URL (blocks command injection), extracts the repo name, and clones it. URL validation only allows github.com, gitlab.com, and bitbucket.org HTTPS URLs.

project.json

Each project directory contains a project.json with metadata:

{
  "id": "a1b2c3d4",
  "name": "My Project",
  "rootPath": "/srv/dev/sarab/repos/my-project",
  "repoUrl": "https://github.com/user/my-project.git",
  "createdAt": "2026-05-09T12:00:00.000Z",
  "updatedAt": "2026-05-09T14:30:00.000Z",
  "settings": {
    "defaultModel": "claude-sonnet-4-6",
    "defaultExecutionMode": "api",
    "defaultSessionMode": "resume"
  }
}

Atomic Writes

All file writes follow an atomic pattern to prevent corruption:

  1. Write to a temporary file (target.<uuid>.tmp)
  2. Call renameSync(tmp, target) (atomic on POSIX)

This is used by writeProjectMeta (fs-utils.ts), persistAll on both JobStore and TicketStore, and all markdown writes. Appends (persistOne) skip the tmp file for performance but only add new data.

Startup Loading Sequence

Both JobStore and TicketStore follow the same startup pattern:

constructor()
  1. loadCache()          — Parse JSONL file into in-memory Map
  2. loadFromMarkdown()    — Scan projects/ directories for .md files
                           and add any NOT already in the Map

ProjectStore.list() calls scanProjectDirs() on every invocation, reading each project.json fresh from disk — no cache.

JSONL as Secondary Cache

JSONL files (jobs.jsonl, tickets.jsonl) serve as a fast-access cache alongside the canonical markdown files. The in-memory Map is the primary working state. On mutation:

  • peristOne (create) — appends one JSON line to the .jsonl file
  • peristAll (update/delete) — rewrites entire JSONL atomically via tmp + rename
  • writeMarkdown — creates/updates the .md file for project-linked items

Migration Notes

The persistence layer replaced an earlier volatile in-memory store. Key changes:

  • Tickets move from in-memory arrays to file-backed TicketStore
  • Project directories are the single source of truth for project-linked data
  • JSONL files auto-populate from existing markdown on first load — no migration script needed
  • Old test fixtures that mocked in-memory state were updated to use temporary directories via mkdtempSync
  • The safeFilenameWithId helper ensures filenames remain unique after title changes
