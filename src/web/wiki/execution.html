Execution & Heartbeat

SARAB's job execution system handles the full lifecycle of Claude CLI invocations: spawning the process, streaming output in real-time, detecting idle or hard timeouts, retrying on failure, and supporting stop/resume for long-running terminal sessions.

Heartbeat mode is the default. When timeoutMs is 0 (the default), there is no hard deadline — jobs run indefinitely until completion. The idle heartbeat system provides proactive detection of stuck processes.

Execution Modes

Each job carries an executionMode field controlling how the prompt is dispatched:

ModeDescription
"api"One-shot Claude CLI execution via -p "prompt". Default mode. Supports stop/resume, heartbeat, and session capture.
"terminal"Runs from the project root directory. Supports stop/resume with live log streaming and process group management.

The executor is selected by the AIProvider type in settings:

Provider typeExecutor classMechanism
claude-cliClaudeExecutorchild_process.spawn("claude", [...flags, "-p", prompt])
openai-compatibleDeepSeekExecutorHTTP POST to OpenAI-compatible API endpoint

Session Modes

The sessionMode field controls whether a job resumes a previous Claude conversation or starts fresh:

sessionModesessionIdBehavior
(unset) / "new"—Fresh invocation, no --resume flag. Always starts a new conversation.
"resume"setResumes the specified session: --resume <sessionId>
"resume"unsetResolves to the latest session for the job's projectId via SessionStore.getLatestForProject()
"latest"—Same as above — resume latest session for the project.

Sessions are captured from Claude CLI stderr using the regex /Session ID: (cls_\w+)/ and persisted to the SessionStore on successful completion.

// Session resolution logic from queue/manager.ts
if (job.sessionMode === "resume" && job.sessionId) {
  execInput.sessionId = job.sessionId;
} else if (job.sessionMode === "latest" ||
           (job.sessionMode === "resume" && !job.sessionId)) {
  const latest = sessionStore.getLatestForProject(job.projectId ?? null);
  if (latest) execInput.sessionId = latest.sessionId;
}

Heartbeat & Timeout Model

SARAB uses a dual-timeout system managed inside ClaudeExecutor.execute():

Hard timeout (timeoutMs)

When set to a value > 0, a setTimeout fires after that many milliseconds and sends SIGTERM to the process group. Default is 0 (no hard deadline).

if (input.timeoutMs > 0) {
  hardTimer = setTimeout(() => {
    timedOut = true;
    killProcessGroup(proc);
  }, input.timeoutMs);
}

Idle timeout (idleTimeoutMs)

A separate timer resets on every stdout chunk. If no output arrives within idleTimeoutMs, the process is killed. This detects hung or silently failing processes without imposing an arbitrary wall-clock limit.

const resetIdleTimer = () => {
  if (idleTimer) clearTimeout(idleTimer);
  if (input.idleTimeoutMs > 0) {
    idleTimer = setTimeout(() => {
      idleTimedOut = true;
      killProcessGroup(proc);
    }, input.idleTimeoutMs);
  }
};
// Reset on every stdout chunk
proc.stdout?.on("data", (chunk) => {
  onOutput(chunk);
  onHeartbeat();
  resetIdleTimer(); // Activity = reset idle clock
});

Stop / Resume Flow

The stop signal flow uses process group signaling for reliable child-process termination:

// From src/executor/claude.ts
function killProcessGroup(proc: ChildProcess): void {
  if (!proc.pid) return;
  try {
    process.kill(-proc.pid, "SIGTERM");  // Signal the whole group
  } catch {
    proc.kill("SIGTERM");                 // Fallback to single process
  }
  setTimeout(() => {
    try {
      process.kill(-proc.pid!, "SIGKILL"); // Hard kill after 10s grace
    } catch {
      proc.kill("SIGKILL");
    }
  }, 10_000);
}
EndpointActionJob status transition
POST /api/jobs/:id/stopCalls executor.kill() which invokes killProcessGroup() — SIGTERM then SIGKILL after 10srunning → stopped
POST /api/jobs/:id/resumeCreates a fresh pending job preserving the original attempt count and linking via resumedFromstopped → pending
// QueueManager.stopJob — from src/queue/manager.ts
stopJob(jobId: string): Job {
  const job = this.jobStore.get(jobId);
  if (job.status !== "running" && job.status !== "retrying")
    throw new ValidationError("...");
  if (this.executor.kill) this.executor.kill();
  const updated = this.jobStore.update(jobId, {
    status: "stopped",
    completedAt: new Date().toISOString(),
    stoppedAt: new Date().toISOString(),
    error: "Stopped by user",
  });
  this.emit("job-cancelled", { type: "job-cancelled", job: updated });
  return updated;
}

SSE Events

The SSEManager subscribes to QueueManager events and broadcasts them to all connected browser clients:

EventPayloadWhen
job-startedFull Job objectJob transitions from pending to running
job-completedFull Job object (exitCode=0)Process exits cleanly
job-failedFull Job objectProcess exits non-zero or executor throws
job-cancelledFull Job objectUser cancels (pending) or stops (running)
job-heartbeat{ jobId, at }Every stdout chunk from the running process
job-retryingFull Job objectRetry attempt begins after exponential backoff
statsQueueStats objectEvery queue poll tick

The heartbeat event is not rate-limited — it fires on every stdout write, providing real-time activity indicators in the queue UI.

// SSEManager subscribes to QueueManager events
queueManager.on("job-started",   (e) => broadcast("job-started",   e.job));
queueManager.on("job-completed", (e) => broadcast("job-completed", e.job));
queueManager.on("job-failed",    (e) => broadcast("job-failed",    e.job));
queueManager.on("job-cancelled", (e) => broadcast("job-cancelled", e.job));
queueManager.on("job-retrying",  (e) => broadcast("job-retrying",  e.job));
queueManager.on("job-heartbeat", (e) => broadcast("job-heartbeat", e));
queueManager.on("queue-tick",    ()  => broadcast("stats", jobStore.stats()));

Concurrency & Queue Polling

The queue runs a fixed-interval poll loop (pollIntervalMs, default 5000ms). Each tick:

  1. Computes available capacity: concurrency - activeJobs.size
  2. Fetches up to that many pending jobs via JobStore.getNextPending()
  3. Markets each as running and emits job-started
  4. Schedules the next tick immediately (does not wait for jobs to finish)
// From src/queue/manager.ts — tick()
const capacity = this.concurrency - this.activeJobs.size;
for (let i = 0; i < capacity; i++) {
  const job = this.jobStore.getNextPending();
  if (!job) break;
  this.activeJobs.add(job.id);
  started.push(this.processJob(job));
}
this.scheduleNext(); // Next tick independent of job completion

Note: Default concurrency is 1. Jobs are processed sequentially. Concurrency > 1 is supported but JSONL storage requires careful handling of concurrent writes (uuid-based tmp filenames prevent conflicts).

Retry with Exponential Backoff

When a job fails (non-zero exit code), processJob retries up to maxRetries times with exponential backoff capped at 60 seconds:

for (let attempt = 0; attempt < maxAttempts; attempt++) {
  if (attempt > 0) {
    const delay = Math.min(2000 * Math.pow(2, attempt - 1), 60_000);
    await sleep(delay);
  }
  // ... execute attempt ...
}

The backoff progression: 2s, 4s, 8s, 16s, 32s, 60s (cap), 60s, ...

Error Recovery & Stale Jobs

On startup, QueueManager.recoverStaleJobs() scans the store for any jobs stuck in running or retrying status (left over from a crash) and marks them as failed with a descriptive message:

private recoverStaleJobs(): void {
  const stale = this.jobStore.list()
    .filter((j) => j.status === "running" || j.status === "retrying");
  for (const job of stale) {
    this.jobStore.update(job.id, {
      status: "failed",
      error: "Server restarted — job was in progress",
      completedAt: new Date().toISOString(),
    });
  }
}

The executor execute() call is wrapped in try/catch within processJob. If the executor throws an unexpected error (not a normal non-zero exit), the job is immediately marked failed with exitCode: -1 and the error message is captured.

Job Lifecycle Diagram

pending ──→ running ──→ completed (exitCode=0)
  │            │
  │            ├──→ failed (non-zero exit / executor error)
  │            ├──→ stopped (user stop request)
  │            └──→ retrying ──→ running (backoff delay)
  │
  └──── cancelled (user cancels while pending)

stopped ──→ pending (resume)
failed  ──→ pending (retry, resets attempt to 0)
