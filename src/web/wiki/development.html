Development Guide

SARAB is a Node.js/Express application with a vanilla JS frontend, filesystem-backed storage, and zero external databases. This guide covers code organization, conventions, and common pitfalls.

Code Conventions

  • One concern per file. Each module has a single responsibility. Storage, API routes, executors, and views each live in their own files.
  • AppError hierarchy. All thrown errors extend AppError. Raw new Error is never used for operational errors. Hierarchy: AppError → NotFoundError (404), ValidationError (400). Express error middleware catches all AppError instances and returns structured JSON responses.
  • Config defaults flow from src/config.ts. Environment variables are read in one place and passed to constructors — never hardcoded in multiple locations.
  • Vanilla JS frontend. No React, no bundler, no build step. The frontend is plain JS served as static files from src/web/. State management is global (currentView, jobs[], etc.) — no reactive framework.
  • API routes use factory functions. Each route module exports createXxxRouter(dep1, dep2) returning an Express Router. Dependencies are injected at wiring time.
  • SSE events use named types: job-started, job-completed, job-failed, job-cancelled, job-retrying, stats.

No TypeScript in JS Files

All frontend code in src/web/ must be valid plain JavaScript. TypeScript annotations (: any, : string, etc.) are forbidden. The node -c check in run-all-tests.sh validates this on every full test run.

# Verify JS syntax:
node -c src/web/js/core.js
node -c src/web/js/views/queue.js

Dependency Injection

DI is manual and linear — no container, no decorators. All wiring happens in src/server.ts:

// Pseudocode for the wiring pattern
const stores = { jobStore, projectStore, sessionStore, settingsStore };
const sseManager = new SSEManager();
const claudeExecutor = new ClaudeExecutor(config, sseManager);
const queueManager = new QueueManager(stores, claudeExecutor, sseManager);

const app = express();
app.use("/api/jobs", createJobRouter(jobStore, queueManager));
app.use("/api/projects", createProjectRouter(projectStore, jobStore));

Known Pitfalls

  • JSONL scaling: JobStore.list() reads the entire file into memory on every call. Fine for <1000 jobs, degrades linearly beyond that. No database — just JSONL and markdown files.
  • Single-threaded queue: Only one Claude invocation runs at a time by default (SARAB_CONCURRENCY=1). Increasing concurrency may cause resource contention.
  • SSE curl hangs: SSE endpoints never close the connection. Always use --max-time N when curling SSE endpoints in scripts or tests.
  • Job cancel race: The queue poll loop may pick up a job between your cancel request and when it processes. Pause the queue first (POST /api/queue/pause) in tests before manipulating pending jobs.
  • Playwright worker conflict: Two parallel workers can collide on JSONL writes. The uuid-based temp file naming prevents corruption, but the config forces workers: 1 to avoid interference.
  • Port in tests: Smoke tests pass PORT via env (env PORT=XXXX npx tsx src/server.ts). The config reads process.env.PORT, not CLI arguments.
  • TypeScript syntax in JS: Never write : any or other TS annotations in src/web/ files. The node -c JS syntax check will reject them.
  • Default provider cannot be deleted: The settings system requires at least one provider. Deleting the default provider returns a 400 error. Set another provider as default first.

Commit Style

Commits use concise messages focused on why rather than what. The format is a single sentence (or two) in the imperative mood, followed by a Co-Authored-By trailer:

Add Kanban board with ticket management and project AI settings

Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
