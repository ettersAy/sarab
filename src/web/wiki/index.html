SARAB — Smart AI Request Automation Bot

A web UI for queuing and executing Claude CLI prompts with real-time SSE monitoring, project context management, Kanban board, and an AI project chatbot.

Quick Links Quick Start Guide Architecture Diagram Full API Reference Project Chatbot Test Guide

Quick Start

# Install
npm install

# Start dev server (port 3457)
npm run dev

# Run tests
npx tsc --noEmit             # Type check
./scripts/smoke-test.sh      # 16 API checks
npx playwright test          # 97 browser tests

Server starts at http://localhost:3457. The web UI loads automatically.

Architecture

Browser (SSE) → Express server → QueueManager (poll loop) → ClaudeExecutor (spawn claude CLI)
                              → JobStore + ProjectStore + TicketStore + ChatStore (JSONL + filesystem)
                              → LogStore (files) + SettingsStore (JSON)
                              → Executor (Claude CLI / DeepSeek HTTP) for prompt improvement & chatbot

Persistence Architecture

Projects, tickets, and prompts persist to the filesystem under /srv/dev/sarab/projects/. JSONL files in data/ provide secondary caching.

Directory Layout

/srv/dev/sarab/projects/
  └── my-project/                  # slugified project name
      ├── project.json             # { id, name, rootPath, createdAt, updatedAt, settings }
      ├── tickets/
      │   └── backlog/
      │       └── my-ticket-xxxxxxxx.md   # markdown with metadata + content
      └── prompts/
          └── my-prompt-xxxxxxxx.md       # markdown with metadata + prompt

Error Handling Rules

  • Malformed markdown files → skipped with warning, never crash
  • Path traversal in project names → 400 ValidationError
  • Duplicate project directory → 400 "Project folder already exists: [slug]"
  • Project name with only special chars → 400 from slugify producing empty result

Project Chatbot

The chatbot lets users ask questions about a selected project, with AI answers grounded in project documentation.

How It Works

  1. User selects a project and asks a question
  2. Server loads context files defined in Project Settings → contextFiles
  3. Context is assembled with safety checks: path traversal blocked, file size limit (50KB/file, 100KB total), missing files flagged
  4. AI prompt is built: system instruction + project name + context files + user question
  5. Response is returned with metadata about which context files were used

Data Model

ChatConversation { id, projectId, title, model, createdAt, updatedAt }
ChatMessage { id, conversationId, role: "user"|"assistant", content, contextFiles[], model, error, createdAt }

Code Conventions

  • One concern per file
  • AppError hierarchy for all thrown errors (no raw new Error)
  • Config defaults flow from config.ts → constructors (not hardcoded twice)
  • Storage: JSONL per entity + filesystem for projects
  • Frontend: vanilla JS, no framework or bundler
  • No TypeScript syntax in JS files — no : any annotations
  • API convention: factory functions createXxxRouter(dep1, dep2) returning Express Router
  • DI: manual linear wiring in server.ts, no container needed
  • Run node -c after every JS edit

Known Pitfalls

  • JSONL storage: JobStore.list() reads entire file per call — fine for <1000 jobs, degrades linearly. No DB.
  • Single-threaded queue: Only one Claude invocation at a time.
  • Port in tests: Smoke tests must pass PORT via env: env PORT=XXXX npx tsx src/server.ts.
  • SSE curl hangs: Always use --max-time N when curling SSE endpoints.
  • Job cancel race: Queue may pick up a job before you cancel it. Pause queue first in tests.
  • Claude CLI: Uses --dangerously-skip-permissions. Ensure claude is in PATH.
  • No framework: Frontend is vanilla JS. No React, no bundler.
  • TS syntax in JS: Do NOT use : any or other TypeScript annotations in JS files.
  • Settings: Default provider cannot be deleted. At least one provider must exist.
  • Settings wiring: When adding storage, ALWAYS add runtime integration in the same commit.
